---
name: task
description: Создать или продолжить задачу кита по ID, выбрать достаточный процесс по риску и провести до проверенной приёмки.
---

Вызов: $task <ID> или $task new "заголовок".

1. Открой tasks/<ID>.md и «Как продолжить», сверь git status/log. Для new обнови доску .codex/workflow/board.js, выбери свободный ID и создай задачу из шаблона без перезаписи существующей.
2. Запиши цель, размер S/M/L, критерии и риски. Прочитай docs/memory/project.md и только релевантные домены workflow-memory. S можно выполнить напрямую. Для M/L нужен продуктовый и архитектурный анализ; отдельных критиков выбирай по риску, не по квоте.
3. Для M/L примени $spec <ID>, получи явное утверждение пользователя и запусти .codex/workflow/spec.js check <ID>. Для бага — $debug <ID>. Не меняй требования молча.
4. Зафиксируй базу диффа, зоны файлов и общие ресурсы сборки/тестов. При делегировании бриф содержит отдельную строку Workflow-Task: <ID>, cwd, результат, путь к спеке M/L, зону, ограничения и команду проверки. Используй роли из инструкций проекта. Агенты не коммитят и не пишут в общие журналы.
5. Исполнитель проверяет изменённое поведение. DONE → ревью; DONE_WITH_CONCERNS → разбор сомнений; NEEDS_CONTEXT → дополнить бриф; BLOCKED → изменить подход, не отправлять тот же бриф повторно.
6. Независимое ревью для M/L и рискованных изменений, точечная самопроверка для малой S. Ревьюер сверяет дифф с контрактом; отчёт исполнителя проверяется. У замечания нужны сценарий и тяжесть, у отказа — причина. После трёх раундов без прогресса пересмотри подход, после пяти с блокерами объясни препятствие.
7. Приёмка: дифф, достигнутые ветки/сценарии, команды/cwd/коды/счётчики, отмеченные критерии. Не повторяй полный прогон без изменения проверяемых файлов или сомнения в результате. Для UI нужна проверка в браузере. Только после этого done, обновление доски и разрешённый локальный коммит.
8. Обновляй «Как продолжить» после значимого шага. Новый подтверждённый повторяемый урок сохрани через workflow-memory; не сохраняй всю историю задачи.
