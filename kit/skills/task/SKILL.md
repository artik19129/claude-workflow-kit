Чек-лист для оркестратора. Сам код не пишешь и поиск не ведёшь — это делают агенты. Для M и L источник требований — спека (`/spec`), для S — бриф.

## 1. Завести или открыть задачу
- `/task new "<заголовок>"`: прочитать `tasks/_index.md`, взять «Следующий ID», создать `tasks/<ID>.md` из `tasks/_template.md`, вписать постановку CEO дословно, `status: discuss`.
- `/task <ID>`: открыть `tasks/<ID>.md`, начать с раздела «Как продолжить». После сжатия контекста — файл задачи и `git log`, не память.
- Баг (`type: bug`) — вести по `/debug`: сначала корневая причина, потом правка.

## 2. Определить размер
Предложить CEO размер (он может переназначить):
- **S** — конфиг, текст, точечная правка по образцу. Без критиков и без спеки: цель, критерии приёмки и проверка — в брифе.
- **M** — фича в одной зоне. Критики, спека.
- **L** — эпик, несколько зон. Критики, спека-дизайн, разбиение на M со ссылкой на ту же спеку.
Сомнение между S и M решается в пользу M: «назову S, чтобы не писать спеку» — это и есть сомнение.

## 3. Критики (только M и L)
- Заспавнить `product-critic` и `arch-critic` параллельно в фоне; для UI-задач после них ещё `ui-designer`. Завершить ход.
- Когда критики вернутся: свести ответы в раздел «Уточнение» файла задачи. CEO показать только спорное — расхождения между критиками, альтернативы, вопросы с вариантами по умолчанию.
- Ответы CEO записать в «Решения» (кто, когда).

## 4. Спека (только M и L)
- `/spec <ID>`: создать `docs/specs/<ID>-<slug>.md`, заполнить из «Уточнения» и «Решений», прогнать `node .claude/hooks/spec.js check <ID>`, показать CEO путь и спорные места, после явного «ок» — `node .claude/hooks/spec.js approve <ID>`.
- Только после этого `status: approved`. Критерии приёмки в файле задачи — копия из спеки или ссылка на неё.
- Для L спека описывает зоны; каждая зона становится задачей M с тем же полем `spec:` во frontmatter, L-файл остаётся зонтиком со ссылками.

## 5. Брифы исполнителям
- Один бриф на зону из «Зоны работ» спеки; обязательные поля — по секции CLAUDE.md кита. Для M/L в брифе путь к спеке и имя зоны, а не пересказ; для S — цель, критерии и проверка прямо в брифе.
- Указать тест, который доказывает результат (RED → GREEN в отчёт), или «без теста, потому что …».
- Агентов запускать только в фоне; зоны параллельных агентов не пересекаются по файлам. Записать базовый коммит (`git rev-parse HEAD`) в «План» — по нему потом берётся дифф для ревью.
- `status: in_progress`; обновить «План» и «Журнал».

## 6. Отчёт исполнителя
Первая строка отчёта — статус:
- **DONE** → к ревью.
- **DONE_WITH_CONCERNS** → прочитать сомнения: про корректность или объём — закрыть до ревью (уточнение тому же агенту через SendMessage), наблюдения — в «Журнал».
- **NEEDS_CONTEXT** → дать недостающее тому же агенту, не перезапускать.
- **BLOCKED** → что-то изменить: контекст, модель (sonnet → opus), дробление зоны, правка спеки через CEO. Тот же бриф той же моделью повторно не отправлять.

## 7. Ревью
- S: ревью — приёмка оркестратором по диффу; `review-opus` — если дифф задел деньги, данные, персистентность или контракт.
- M/L: `review-opus` на дифф от базового коммита (`git diff <base>..HEAD`, не `HEAD~1`), обязательно не тем агентом, что писал код; в брифе путь к спеке, зона, отчёт исполнителя как непроверенные утверждения. `status: review`.
- По каждому замечанию вердикт оркестратора в раздел «Ревью»: принято / отклонено с причиной / уточнить. Молча выбросить нельзя. Minor — в «Журнал», в цикл правок не идут.
- Цикл правок, не больше пяти раундов: раунд = замечания исполнителю + повторное ревью только по списку замечаний и диффу правок. Раунды 1–3 — тому же исполнителю через SendMessage («Продолжаю: …»); раунды 4–5 — новый `impl-opus` с брифом, отчётом предшественника и открытыми замечаниями. Перед повторным ревью убедиться, что в отчёте о правке есть покрывающие тесты, команда и вывод.
- После пятого раунда — стоп: по каждому открытому замечанию решение с записью в «Решения» (ревьюер неправ / реально, но не блокирует / реально и блокирует → CEO).

## 8. Приёмка
- Прочитать дифф самому. Прогнать проверки проекта (команды из CLAUDE.md проекта: typecheck, lint, селфтесты) и записать в раздел «Приёмка» файла задачи команду, код выхода и счётчики. Без этих строк задача не закрывается.
- Грепнуть новые комментарии в изменённых файлах и убедиться, что они не пересказывают код.
- Пройти критерии приёмки спеки (для S — брифа) по одному галочками. Регрессионный тест бага — проверить, что без правки он падает.
- `status: acceptance` → `done`.

## 9. Журнал и коммит
1. Если у проекта есть CHANGELOG — сделать запись по его правилам.
2. Обновить файл задачи: `status: done`, «Статус», «Журнал», «Как продолжить».
3. Перегенерировать доску `node .claude/hooks/board.js`.
4. Сделать один коммит `type(<ID>): что` с явным списком файлов: изменённые исходники + `CHANGELOG.md` (если менялся) + `tasks/<ID>.md` + `tasks/_index.md` + `docs/specs/<ID>-*.md` (если есть).
5. Отчитаться CEO: хеш коммита, текст записи ченж-лога и список «Решения, принятые без CEO» из раздела «Решения» (все с пометкой «оркестратор», с ценой ошибки). Push и PR — только по явной просьбе CEO.

## 10. После каждого шага
Обновить в файле задачи «Статус», «Журнал», «Как продолжить»; перегенерировать доску `node .claude/hooks/board.js`. Решение, принятое без CEO, — сразу в «Решения» с пометкой «оркестратор».
