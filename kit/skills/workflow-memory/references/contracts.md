# Контракты и перенос реализации

- Сверяй план с текущей схемой, исходником и поведением. Историческая спека или память может отставать. Расхождение предъяви как конкретный вход → два разных результата; не меняй утверждённый контракт молча.
- При переносе API проверь HTTP-статус, форму ответа, null/пустые коллекции, порядок валидации, авторизацию, идемпотентность и атрибуцию автора. Дефолты нового фреймворка могут незаметно изменить контракт.
- Найди потребителей изменённого типа/события/API. В другом репозитории явно задай cwd, версию общего пакета и порядок обновления. Обновление только производителя не завершает изменение контракта.
- Границы слоёв следуют проекту. Не превращай правило «всё через классы» или конкретный фреймворк одного продукта в требование ко всем проектам.
- Спека определяет продуктовый результат; устаревшая деталь плана не оправдывает заведомо неверное поведение. Изменение требований согласуй; исправление ошибочного предположения внутри согласованного результата запиши с доказательством.

Основание: vualya-crm, `phase10-plans-vs-express-source`, `nestjs-api-rewrite-gotchas`, `vualya-site-repo`; vualya-site README о пакетах контрактов и источнике страниц. Пересмотр 2026-10-15.
