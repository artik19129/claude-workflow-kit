# Задачи

Каталог `tasks/` — рабочая доска проекта. Живёт в git вместе с кодом.

## Правила

- Источник правды по задаче — её файл `VC-042.md`. Всё состояние задачи (постановка, решения, план, журнал) только там.
- `_index.md` генерируется командой `node .claude/hooks/board.js` из frontmatter файлов задач. Руками не править — перезапишется.
- Единственный, кто пишет в файл задачи, — оркестратор. Агенты-исполнители отдают отчёт, оркестратор переносит результат в файл.
- Раздел «Как продолжить» обновляется после каждого значимого шага: решение CEO, спавн агента, результат, ревью, приёмка, коммит.
- Новая задача: скопировать `_template.md` в `VC-NNN.md`, где NNN — «Следующий ID» из `_index.md`.
- «Следующий ID» считается по именам файлов `VC-NNN.md`, а не по полю `id`. Каноничный ID задачи — имя файла: если `id` во frontmatter другой, задача попадёт в доску под именем файла, а расхождение уедет в «Не распознано».
- Файлы с битым frontmatter не теряются: они попадают в секцию «Не распознано» с причиной, а не выпадают из доски.
- ID задачи идёт в scope коммита: `type(VC-042): что сделано`.
- Во frontmatter заголовок с `#` или начинающийся с кавычки — в кавычках: `title: "Bug #42 в экспорте"`. Без кавычек всё от ` #` до конца строки считается YAML-комментарием и в доску не попадёт.
- Поле `type: bug` — задача ведётся по `/debug`: сначала корневая причина, потом правка с регрессионным тестом.
- Решения, принятые оркестратором без CEO, пишутся в «Решения» с пометкой «оркестратор», датой и ценой ошибки и перечисляются CEO при сдаче.
- Раздел «Приёмка (свидетельства)» заполняется командами и их результатами (код выхода, счётчики); без них задача не переводится в `done`.

## Спека

- Для задач M и L источник требований — спека `docs/specs/VC-NNN-<slug>.md`, путь к ней — в поле `spec:` frontmatter. Создаётся командой `node .claude/hooks/spec.js new VC-NNN <slug>` из `docs/specs/_template.md`, проверяется `node .claude/hooks/spec.js check VC-NNN`, после явного «ок» CEO утверждается `node .claude/hooks/spec.js approve VC-NNN`.
- Брифы исполнителей и ревьюера ссылаются на спеку и зону, а не пересказывают её. Stop-хук блокирует ход, если `impl-*` или `review-opus` запущен по задаче M/L без пути к утверждённой спеке в брифе.
- Изменение утверждённой спеки — только через CEO: `status: draft` → правка → `check` → `approve`.
- Для S спека не нужна: цель, критерии приёмки и проверка пишутся в брифе.

## Статусы

| Статус | Смысл |
|---|---|
| `backlog` | записана, в работу не берём |
| `discuss` | нужен ответ CEO: постановка, приоритет, размер, апрув спеки |
| `approved` | CEO согласовал (для M/L — спека утверждена), можно брать в работу |
| `in_progress` | пишется код |
| `review` | дифф у ревьюера, идёт цикл правок (не больше пяти раундов) |
| `acceptance` | замечания закрыты, идёт приёмка оркестратором |
| `done` | принята |
| `blocked` | ждёт внешнего события или решения CEO |

Секции доски: «В работе» — `approved`, `in_progress`, `review`, `acceptance`; «Ждёт CEO» — `discuss`, `blocked`; «Бэклог» — `backlog`; «Готово» — `done`.

## Размеры

- **S** — конфиг, текст, правка по готовому образцу. Без критиков и без спеки: оркестратор пишет бриф с целью, критериями и проверкой, impl-sonnet делает, оркестратор принимает.
- **M** — фича в одной зоне. product-critic и arch-critic уточняют постановку → спека → апрув CEO → impl → review-opus → приёмка.
- **L** — эпик. Критики и спека-дизайн с зонами; задача разбивается на несколько M с тем же полем `spec`; сам L-файл остаётся зонтиком со ссылками.

Сомнение между S и M решается в пользу M.

## Решения

Решения, влияющие больше чем на одну задачу, дублируются в `docs/decisions.md`. Локальные остаются в файле задачи.
