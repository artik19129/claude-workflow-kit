# Задачи

Каталог `tasks/` — рабочая доска проекта. Живёт в git вместе с кодом.

## Правила

- Источник правды по задаче — её файл `VC-042.md`. Всё состояние задачи (постановка, решения, план, журнал) только там.
- `_index.md` генерируется командой `node .claude/hooks/board.js` из frontmatter файлов задач. Руками не править — перезапишется.
- Единственный, кто пишет в файл задачи, — оркестратор. Агенты-исполнители отдают отчёт, оркестратор переносит результат в файл.
- Раздел «Как продолжить» обновляется после каждого значимого шага: решение CEO, спавн агента, результат, ревью, приёмка, коммит.
- Новая задача: скопировать `_template.md` в `VC-NNN.md`, где NNN — «Следующий ID» из `_index.md`.
- «Следующий ID» считается по именам файлов `VC-NNN.md`, а не по полю `id`. Каноничный ID задачи — имя файла: если `id` во frontmatter другой, задача попадёт в доску под именем файла, а расхождение уедет в «Не распознано».
- Файлы с битым frontmatter не теряются: они попадают в секцию «Не распознано» с причиной, а не выпадают из доски.
- ID задачи идёт в scope коммита: `type(VC-042): что сделано`.
- Во frontmatter заголовок с `#` или начинающийся с кавычки — в кавычках: `title: "Bug #42 в экспорте"`. Без кавычек всё от ` #` до конца строки считается YAML-комментарием и в доску не попадёт.

## Статусы

| Статус | Смысл |
|---|---|
| `backlog` | записана, в работу не берём |
| `discuss` | нужен ответ CEO: постановка, приоритет, размер |
| `approved` | CEO согласовал, можно брать в работу |
| `in_progress` | пишется код |
| `review` | дифф у ревьюера |
| `acceptance` | замечания закрыты, идёт приёмка оркестратором |
| `done` | принята |
| `blocked` | ждёт внешнего события или решения CEO |

Секции доски: «В работе» — `approved`, `in_progress`, `review`, `acceptance`; «Ждёт CEO» — `discuss`, `blocked`; «Бэклог» — `backlog`; «Готово» — `done`.

## Размеры

- **S** — конфиг, текст, правка по готовому образцу. Без критиков: оркестратор пишет бриф, impl-sonnet делает, оркестратор принимает.
- **M** — фича в одной зоне. product-critic и arch-critic уточняют постановку → апрув CEO → impl → review-opus → приёмка.
- **L** — эпик. arch-critic пишет дизайн-записку, задача разбивается на несколько M; сам L-файл остаётся зонтиком со ссылками.

## Решения

Решения, влияющие больше чем на одну задачу, дублируются в `docs/decisions.md`. Локальные остаются в файле задачи.
