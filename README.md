# AI Workflow Kit — Claude Code и Codex

Переносимый набор для работы в Claude Code и Codex: скиллы, доска задач, спеки, шаблоны и проектные хуки дисциплины. Для обоих клиентов устанавливаются все семь ролей агентов. Настройки размещаются в проекте, а не в личном профиле. Имя репозитория и пакета `claude-workflow-kit` сохранено для совместимости.

## Поддержка двух клиентов (1.4)

```sh
node install.js install <путь-к-проекту> --target both
node install.js install <путь-к-проекту> --target codex
node install.js update <путь-к-проекту> --target both
node install.js status <путь-к-проекту> --target both
node install.js uninstall <путь-к-проекту> --target codex
```

`--target claude|codex|both` работает для всех четырёх команд. Без флага всегда выбирается **claude**, чтобы старые команды не меняли смысл. Для обновления или удаления обоих адаптеров указывайте `--target both` каждый раз. Установка Codex рядом с уже установленным Claude: `install --target codex`; обратный порядок тоже поддерживается.

| Возможность | Claude Code | Codex |
|---|---|---|
| Инструкции | блок в `CLAUDE.md` | блок в `AGENTS.md` |
| Навыки | `.claude/skills/`, `/task` | `.agents/skills/`, `$task` |
| Доска и спеки | `.claude/hooks/board.js`, `spec.js` | `.codex/workflow/board.js`, `spec.js` |
| Делегирование | агенты из `.claude/agents/` | семь профилей `.codex/agents/*.toml`, GPT-6 Sol |
| Автоматические хуки | settings.json, Stop-гейт и контекст | hooks.json: контекст, PreToolUse-гейт спеки, Stop-проверка приёмки |
| Состояние установки | `.claude/kit.json` | `.codex/workflow-kit.json` |
| Задачи и документы | общие `tasks/`, `docs/specs/`, `docs/decisions.md` | те же файлы |

В Codex доступны `$task new "Название"`, `$task VC-001`, `$spec VC-001`, `$debug VC-001`, `$board`, `$release` и `$ui-ux-pro-max`. После установки откройте новую сессию Codex в целевом проекте. `AGENTS.override.md` может перекрывать `AGENTS.md`; установщик предупреждает о таком файле.

```sh
node .codex/workflow/board.js --print
node .codex/workflow/spec.js new VC-001 export-csv
node .codex/workflow/spec.js check VC-001
node .codex/workflow/spec.js approve VC-001
```

Последнюю команду агент выполняет только после явного утверждения пользователем. В версии 1.3 добавлены собственные хуки Codex, проверенные живым запуском. В версии 1.4 все семь ролей получили профили GPT-6 Sol; имена opus/sonnet сохранены как идентификаторы ролей.

Codex сохраняет содержимое `AGENTS.md` вне своего блока, чужие навыки и `.codex/config.toml`. Если устанавливаемый файл навыка уже существует и не принадлежит киту, установка отказывает до записи. `update` перезаписывает файлы из манифеста; `uninstall` удаляет перечисленные файлы, блок инструкций и только записи собственных хуков. Чужие обработчики и метаданные в `.codex/hooks.json` сохраняются. Повреждённый JSON или неверная форма hooks отклоняются до записи. Задачи, спеки и пользовательские файлы остаются. Не редактируйте манифест вручную.

`--dry-run` показывает изменения без записи. `--no-design-skill` исключает приватный `emil-design-eng`; в Codex его можно установить только из имеющейся копии `kit/skills/emil-design-eng/`, поиск кэша Claude не запускается. `--node` относится к хукам Claude; команды Codex запускайте через доступный Node.js ≥18.

Codex-адаптер не меняет `.gitignore`: если проект игнорирует `.agents/` или `.codex/`, явно разрешите отслеживание `.agents/skills/`, `.codex/workflow/`, `.codex/hooks.json` и `.codex/workflow-kit.json`. Проверяйте `git status` перед коммитом. Не ведите одну задачу одновременно из двух сессий: файлы состояния общие, блокировки не предусмотрены.

Расположение навыков и инструкций соответствует официальной документации: [Codex skills](https://learn.chatgpt.com/docs/build-skills), [AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md). Исходники адаптера — `lib/codex.js`, инструкции и варианты навыков — `kit/codex/`; скрипты доски и спек общие с Claude.

### Включение хуков Codex

После `install`/`update --target codex` откройте доверенный проект в Codex, выполните `/hooks`, проверьте и разрешите определения AI Workflow Kit. Изменённые определения могут потребовать нового доверия. Установщик не меняет доверие проекта и не включает выключенные пользователем хуки. `status` проверяет файлы/настройки, но не подтверждает, что Codex их исполняет. Требуются включённые lifecycle hooks и Node.js в PATH среды хуков.

- `SessionStart` и `UserPromptSubmit` добавляют краткий контекст задач.
- `PreToolUse` блокирует правки исходников через `apply_patch`, потенциально изменяющие shell-команды и запуск исполнителей/ревьюеров для M/L без валидной спеки со статусом и записью утверждения. Плановые документы разрешены через `apply_patch`; простые команды чтения и команды board/spec — по одной, без пайпов и цепочек. Если безопасный shell-вызов не распознан, он консервативно блокируется до апрува.
- `Stop` для done проверяет наличие записи приёмки и отмеченных критериев. Даёт один дополнительный ход для исправления записи/статуса; не подтверждает достоверность указанных результатов.

ID из запроса выбирает задачу для сессии; несколько ID означают проверку всех указанных задач. Без выбора проверяются активные задачи вне done/backlog. Единственная активная задача запоминается автоматически. `$task new` сбрасывает предыдущий выбор. Состояние выбора хранится в системном temp по хешу пути проекта и session_id, а не в git; файлы задач между сессиями общие.

Хуки являются защитой рабочего процесса, не границей безопасности. Они не покрывают все инструменты/внешние записи, ввод в уже запущенный shell через `write_stdin`, ручную правку статуса утверждения или отключение хуков. Нет задач — нет гейта. Для S гейт спеки не применяется. До апрува новые shell-сессии с неизвестными командами не запускаются. Полное независимое ревью и истинность результатов остаются ответственностью агента и пользователя.

Команда запуска хука находит установленный скрипт вверх от cwd, поэтому работает из подкаталогов и после переноса проекта. Глобальный `~/.codex/hooks.json` установщик не меняет. Формат событий и правила доверия: [официальная документация Codex Hooks](https://learn.chatgpt.com/docs/hooks). Результаты реального отрицательного и положительного тестов: [отчёт хуков](docs/live-hooks-test-2026-09-28.md).

Ниже описаны существующая интеграция **Claude Code** и общий процесс кита.

С версии 1.1 процесс спек-драйвен: для задач M и L источник требований — спека `docs/specs/<ID>-<slug>.md`, утверждённая CEO; брифы исполнителей и ревьюера ссылаются на неё, а Stop-хук не даёт запустить исполнителя или ревьюера без утверждённой спеки.

## Установка

```
node install.js install <путь-к-проекту>
```

Что делает:

- копирует агентов, скиллы и хуки в `.claude/` проекта;
- вставляет секцию кита в `CLAUDE.md` между маркерами `<!-- claude-workflow-kit:start vX.Y.Z -->` и `<!-- claude-workflow-kit:end -->` (файл создаётся, если его нет);
- дописывает хуки кита в `.claude/settings.json`, сохраняя чужие хуки и остальные ключи;
- правит `.gitignore`: блок кита между маркерами `# claude-workflow-kit:start` и `# claude-workflow-kit:end` заменяется целиком; все строки вне блока, игнорирующие `.claude` целиком (`.claude`, `.claude/`, `/.claude/`, `.claude/*`, `**/.claude/`), удаляются, а блок встаёт на место первой из них; если таких строк не было — дописывается в конец;
- создаёт `tasks/README.md`, `tasks/_template.md`, `docs/decisions.md` и `docs/specs/_template.md`, если их ещё нет, и генерирует `tasks/_index.md`;
- пишет `.claude/kit.json` с версией, датой установки и сделанным выбором.

Установка останавливается с кодом 1 и ничего не пишет, если разметка нарушена: в `CLAUDE.md` маркеры кита не парные, в `.gitignore` блок кита не закрыт маркером `# claude-workflow-kit:end`, в чужом `.claude/settings.json` ключ `hooks` не объект или `hooks.<событие>` не массив, явно заданный `--node` не запускается без шелла. Все такие проверки идут до первой записи — полуустановки не бывает. Такие места чинятся руками.

Маркеры кита нельзя цитировать в тексте `CLAUDE.md`, в том числе внутри code-fence: установщик считает их границами своей секции и вырежет всё между ними. Если про маркеры нужно написать, разбивайте строку, чтобы точного совпадения не было.

`.claude/settings.json` читается и с BOM, и без него, а записывается всегда без BOM, с переводами строк как в исходном файле.

### Обновление с 1.0

```
node install.js update <путь>
```

`update` перепишет агентов, скиллы, хуки и секцию `CLAUDE.md`, создаст недостающий `docs/specs/_template.md` и предупредит, если в `tasks/_template.md` проекта нет поля `spec:` — добавьте строку `spec:` во frontmatter шаблона (образец в `kit/templates/tasks/_template.md`; заодно можно добавить `type:` и разделы «Ревью» и «Приёмка (свидетельства)»). Существующие файлы задач кит не трогает. Задачи M/L, которые уже в работе, с этого момента требуют спеку: либо `/spec <ID>` и апрув, либо размер S, если задача действительно на одну зону и без контрактов.

### `.claude/kit.json`

```json
{
  "version": "1.1.0",
  "installed_at": "2026-01-01T00:00:00.000Z",
  "node": null,
  "design_skill": true,
  "created_claude_md": false,
  "created_settings": false
}
```

- `node` — значение `--node`, как его задали при установке (`null`, если флага не было);
- `design_skill` — ставился ли скилл `emil-design-eng`;
- `created_claude_md`, `created_settings` — создавал ли кит `CLAUDE.md` и `.claude/settings.json`; если да, `uninstall` удалит опустевший файл, если нет — оставит.

`update` и `status` без флагов берут `node` и `design_skill` отсюда: `update` не возвращает `command` к `node`, а `status` после установки с `--no-design-skill` не требует скилла. Флаги в командной строке сильнее файла и перезаписывают его.

### Форма хуков

Хуки записываются в `.claude/settings.json` так:

```json
{
  "type": "command",
  "command": "node",
  "args": ["${CLAUDE_PROJECT_DIR}/.claude/hooks/orchestrator-guard.js", "remind"],
  "timeout": 10,
  "statusMessage": "orchestrator-guard: напоминание"
}
```

Отдельный `args` важен: с ним Claude Code запускает процесс напрямую, без шелла, и сам подставляет `${CLAUDE_PROJECT_DIR}`. Однострочная команда на Windows уходит в Git Bash, где запуск node может не работать.

Свой хук кита установщик узнаёт по `args[0]`, который содержит `${CLAUDE_PROJECT_DIR}` и оканчивается на `/.claude/hooks/<файл>.js`: при повторном запуске запись не дублируется, а заменяется; старые однострочные записи кита `update` переводит в новую форму. Чужая запись с похожим хвостом, но абсолютным путём (`C:/other/vendor/.claude/hooks/board.js`), китом не считается — её не трогают ни `install`, ни `uninstall`.

## Остальные команды

```
node install.js update <путь>        обновить части кита; недостающие project-owned файлы создать, существующие не трогать
node install.js status <путь>        что установлено, что отличается, чего нет
node install.js uninstall <путь>     убрать кит, оставив tasks/, docs/decisions.md и docs/specs/
```

`status` печатает выбранные `node` и `design_skill`, состояние kit-owned файлов, секции `CLAUDE.md`, хуков и строку `.gitignore: вне блока нет строк, игнорирующих .claude`. Выходит с кодом 1, если что-то отличается или отсутствует (в том числе если `.claude` игнорируется строкой вне блока кита — тогда агенты и хуки не попадут в git), и предупреждает, если хуки кита записаны в старой однострочной форме.

`uninstall` удаляет блок кита из `.gitignore`, оставляя на его месте строку `.claude/`. Опустевшие `CLAUDE.md` и `.claude/settings.json` он удаляет только если сам их создал (`created_claude_md` / `created_settings` в `kit.json`), иначе оставляет как есть.

Флаги:

- `--dry-run` — показать план без записи.
- `--node <путь к node>` — конкретный интерпретатор в поле `command` хуков (`args` не меняются). Параметр машинно-зависимый: путь верен только для той машины, где ставят кит, и попадает в `settings.json` проекта — по умолчанию там остаётся `node`. Нужен, если проба `node -v` без шелла не прошла и установщик это сказал. Если путь задан флагом `--node` именно в этом запуске и не запускается, установщик останавливается с кодом 1 до любой записи; если путь взят из `kit.json` (флаг не указан) или используется значение по умолчанию (`node`), непройденная проба — только предупреждение, установка продолжается. Выбор запоминается в `kit.json`, поэтому `update` флаг повторять не нужно.
- `--no-design-skill` — не ставить скилл `emil-design-eng` (см. ниже). Тоже запоминается в `kit.json`; вернуть скилл — `--design-skill`.
- `--design-skill` — поставить скилл, даже если в `kit.json` записан отказ.

`update` идемпотентен: второй запуск подряд печатает «без изменений» по всем строкам.

## Процесс: от постановки до коммита

Жизненный цикл ведёт скилл `/task`; размер задачи определяет, сколько процесса ей положено.

| Размер | Критики | Спека | Ревью | Кто делает |
|---|---|---|---|---|
| S — конфиг, текст, правка по образцу | нет | нет: цель, критерии и проверка в брифе | приёмка оркестратором; review-opus, если задеты деньги, данные или контракт | impl-sonnet |
| M — фича в одной зоне | product-critic + arch-critic (+ ui-designer для UI) | `docs/specs/<ID>-<slug>.md`, апрув CEO | review-opus по спеке | impl-opus / impl-sonnet по зоне |
| L — эпик из нескольких зон | те же | спека-дизайн с зонами; каждая зона — задача M с тем же `spec:` | review-opus по спеке | параллельные исполнители по зонам |

Сомнение между S и M решается в пользу M.

Для M и L порядок такой:

1. `/task new "<заголовок>"` — файл задачи, постановка CEO дословно, `status: discuss`.
2. Критики параллельно в фоне; спорное — CEO, ответы — в «Решения».
3. `/spec <ID>` — оркестратор пишет спеку из ответов критиков и решений CEO: цель, «не делаем», поведение, контракты, ограничения, зоны работ (файлы, что зона потребляет и производит, исполнитель, проверка), тесты, критерии приёмки. `node .claude/hooks/spec.js check <ID>` до нуля замечаний, явное «ок» CEO, `node .claude/hooks/spec.js approve <ID>`, `status: approved`.
4. Брифы по зонам: путь к спеке и имя зоны вместо пересказа, тест, который доказывает результат (падение до правки и прохождение после — в отчёт), формат отчёта со статусом `DONE | DONE_WITH_CONCERNS | BLOCKED | NEEDS_CONTEXT`.
5. Ревью review-opus: сначала соответствие спеке (чего нет, что лишнее, что понято не так, что не проверить по диффу), потом блокеры. Вердикт по каждому замечанию — оркестратора, в раздел «Ревью» файла задачи. Цикл правок не больше пяти раундов: раунды 1–3 — тому же исполнителю через SendMessage, 4–5 — новый impl-opus с отчётом предшественника; повторное ревью только по списку замечаний и диффу правок; после пятого раунда — решение оркестратора с записью.
6. Приёмка: дифф, проверки проекта своими руками, команды и результаты — в раздел «Приёмка» файла задачи, критерии спеки галочками.
7. Один коммит на задачу; в него входит и спека. В отчёте CEO — хеш, ченжлог и список решений, принятых без CEO.

Решения без CEO: после апрува спеки оркестратор не останавливает работу вопросами — двусмысленность, конфликт брифа с кодом и выбор между равноценными вариантами он решает сам, записывает в «Решения» с пометкой «оркестратор» и ценой ошибки и перечисляет CEO при сдаче. Остановка — только перед необратимым действием, внешним побочным эффектом (push, PR, трекер), изменением утверждённой спеки и когда спека сломана так, что любой путь — угадывание.

Баги ведутся по `/debug`: симптом → explore-opus ищет корневую причину (воспроизведение, ошибка дословно, недавние изменения, цепочка вызовов до источника, рабочий аналог) → без причины брифа на правку нет → регрессионный тест, который падает до правки, → минимальная правка в источнике → третья неудачная правка означает вопрос об архитектуре, а не четвёртую попытку.

## Спеки

`docs/specs/<ID>-<slug>.md` — project-owned файл, создаётся из `docs/specs/_template.md`:

```
node .claude/hooks/spec.js new <ID> [slug]       создать спеку из шаблона и прописать spec: в tasks/<ID>.md
node .claude/hooks/spec.js check <ID|путь>       проверить: exit 1 и список замечаний, если есть
node .claude/hooks/spec.js approve <ID|путь> [--by <кто>]   check, затем status: approved и дата
```

Общий флаг `--root <корень проекта>`; без него корень берётся от расположения самого скрипта (`.claude/hooks/` → на два уровня выше), затем из `CLAUDE_PROJECT_DIR`, затем из текущего каталога.

`check` находит: отсутствующие или пустые обязательные разделы («Цель», «Не делаем», «Поведение», «Контракты», «Ограничения», «Зоны работ», «Тесты», «Критерии приёмки»); строки, дословно совпадающие с подсказками шаблона проекта; заглушки `TBD`, `TODO`, `FIXME`, `???`, «уточнить»; отсутствие пунктов `- [ ]` в критериях; открытые вопросы без пометки «решено»; расхождение `id` с именем файла; `status` не `draft`/`approved`. `approve` отказывает при любом замечании и не меняет файл.

Frontmatter спеки: `id`, `title`, `status: draft | approved`, `approved: <дата> <кто>`, `updated`. Изменение утверждённой спеки — через CEO: `status: draft` руками, правка, `check`, `approve`.

### Гейт спеки в Stop-хуке

`orchestrator-guard.js stop` в последнем ходе смотрит на каждый вызов `Agent` с `subagent_type` вида `impl-*` или `review-*`. Из текста брифа берутся все ID `VC-NNN`; для каждого читается `tasks/<ID>.md`. Задача считается кандидатом, если её `size` — `M` или `L`, а `status` не `done` и не `backlog`. Ход блокируется (нарушение D), если среди кандидатов нет ни одного с полем `spec:`, чей файл существует, имеет `status: approved` и чей путь встречается в тексте брифа. Причина перечисляет каждого кандидата и что именно не так: нет поля `spec`, файл не найден, статус `draft`, путь не указан в брифе. Ссылка на завершённую задачу как на образец гейт не трогает; агентам explore-opus, критикам и ui-designer гейт не нужен. Если в проекте нет каталога `tasks/`, гейт молчит. Корень проекта: `CLAUDE_PROJECT_DIR`, затем `cwd` из входа хука, затем расположение самого хука.

Как и остальные проверки хука, блокировка срабатывает один раз за ход (`stop_hook_active`): хук просит либо дослать путь к спеке работающему агенту через SendMessage, либо остановить агента и сказать CEO, чего не хватает.

Прочие правила хука: A — на каждый запуск агента в финальном сообщении строка «Заспавнил: …»; B — больше пяти Read/Grep/Glob за ход без агента; C — агент запущен в foreground. Селфтест: `node .claude/hooks/orchestrator-guard.js selftest`; разбор транскрипта по ходам: `node .claude/hooks/orchestrator-guard.js report <transcript.jsonl>`.

## Скиллы

- `/task new "<заголовок>" | <ID>` — жизненный цикл задачи: размер, критики, спека, брифы, отчёты исполнителей, ревью с циклом правок, приёмка, коммит.
- `/spec <ID>` — написать или переутвердить спеку: материал из критиков, заполнение разделов, `check`, апрув CEO, `approve`, изменение после апрува.
- `/debug <ID>` — баг от симптома к корневой причине, регрессионный тест до правки, правило трёх.
- `/board` — доска и вопросы, которые ждут CEO.
- `/release [версия]` — запись в CHANGELOG и предложение коммита.

## Кто чем владеет

**kit-owned** — перезаписывается при `update`, удаляется при `uninstall`:

- `.claude/agents/*.md`, `.claude/skills/<name>/**`, `.claude/hooks/*.js`;
- секция `CLAUDE.md` между маркерами;
- записи хуков кита в `.claude/settings.json`;
- `.claude/kit.json`;
- блок кита в `.gitignore`.

**project-owned** — создаётся один раз и больше не трогается (`update` только досоздаёт недостающие):

- `tasks/*.md` (файлы задач, `README.md`, `_template.md`);
- `docs/decisions.md`;
- `docs/specs/_template.md` и спеки `docs/specs/<ID>-*.md`;
- всё в `CLAUDE.md` вне маркеров;
- все прочие ключи и чужие хуки в `.claude/settings.json`.

`tasks/_index.md` — kit-owned: генерируется из frontmatter задач командой `node .claude/hooks/board.js` и перезаписывается при `install` и `update`. Руками не править.

## Как добавить агента или скилл

1. Положить файл в `kit/agents/<имя>.md` (frontmatter агента Claude Code) или каталог в `kit/skills/<имя>/`.
2. Поднять версию в `VERSION`.
3. В проекте выполнить `node install.js update <путь>`.

Для Codex используйте `--target codex` или `--target both`. Если новый скилл содержит специфические инструменты или роли Claude, добавьте его вариант в `kit/codex/skills/<имя>/SKILL.md`; без такого варианта установщик копирует общий навык с заменой путей скриптов. Файлы `kit/agents/` относятся только к Claude.

Удаление агента из кита не удаляет его из проекта автоматически — файл нужно убрать вручную или выполнить `uninstall` и `install`.

## Доска задач

`tasks/VC-NNN.md` — источник правды по задаче, `tasks/_index.md` собирается из их frontmatter:

```
node .claude/hooks/board.js            перезаписать tasks/_index.md
node .claude/hooks/board.js --print    вывести доску в stdout
node .claude/hooks/board.js <путь>     корень проекта первым аргументом
```

Без аргумента корень берётся от самого хука (`.claude/hooks/` → на два уровня выше), затем из `CLAUDE_PROJECT_DIR`, и только потом из текущего каталога — из подкаталога проекта доска всё равно пишется в корень.

«Следующий ID» считается по именам файлов `VC-NNN.md`, а не по их содержимому, поэтому задача с битым frontmatter не даёт затереть себя новой. Файлы, которые не разобрались, попадают в доску в секцию «Не распознано».

Каноничный ID задачи — имя файла. Если `id` во frontmatter другой, задача всё равно выводится под ID из имени файла, а в «Не распознано» появляется строка «id во frontmatter (VC-042) не совпадает с именем файла».

Frontmatter: значение в кавычках берётся как есть; без кавычек всё от ` #` до конца строки — комментарий; строка вида `spec:   # подсказка` даёт пустое значение. Поля `type` и `spec` доска не показывает, их читают скиллы и гейт спеки.

Правила работы с доской — в `tasks/README.md` после установки.

## Источники

Спек-драйвен цикл, гейт апрува, соответствие спеке как первая часть ревью, статусы отчёта исполнителя, цикл правок с ограничением раундов и повторным ревью только по замечаниям, решения с записью вместо остановок, свидетельства перед заявлением «готово» и путь от симптома к корневой причине адаптированы из методологии [obra/superpowers](https://github.com/obra/superpowers) (MIT) под модель оркестратора кита: оркестратор пишет спеку и брифы, но не код; план с готовым кодом на каждый шаг, отдельные worktree и сценарии слияния веток не переносились.
